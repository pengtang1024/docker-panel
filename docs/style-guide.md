# 文档风格与排版规范

> **一句话**：本页规定 docker-panel 所有对外文档（README、顶层社区文档、`docs/`、两个站的 Wiki）的统一排版写法，目的是让每页都能在 30 秒内回答「这页讲什么、我现在该看哪一节」。
>
> **适用范围**：所有 `*.md`。新增文档必须按本规范写；改旧文档时顺手对齐，不做与本次改动无关的全量重排。

**对应源码**：无（纯文档规范）｜**执行方式**：`docs/agents-rules.md` §6「新增文档」触发表 + PR 检查清单

## 1. 两条不可协商的前提

> [!IMPORTANT]
> **① 两站渲染必须一致效果。** 文档同时出现在 GitHub 与 Gitee，排版只能用**两边都支持**的语法，见 §3。
>
> **② 排版不得改变技术内容。** 美化只动结构、标题、标记、表格与折叠，**不改**任何命令、路径、行号、报错文案、版本号、接口行为。改到不确定的地方保持原样。

## 2. 页头三件套（每页必须有）

```markdown
# 页面标题

> **一句话**：这页回答什么问题 / 给谁看（不超过两行）。

**对应源码**：`src/config.rs`、`ui/app.slint`｜**相关页面**：[故障排查](troubleshooting.md)
```

- 标题只用 `#` 一次，不做「一级标题 + 副标题」两级重复。
- 「一句话」用引用块，**说清读者与用途**，禁止写成标题的同义复述。
- 面向开发者/维护者的页面写「对应源码」，面向最终用户的页面写「相关页面」或「前置知识」。二者都不适用时写 `**适用范围**：...`。

## 3. 两站都支持的语法（只能从这里选）

| 写法 | GitHub | Gitee | 用途 |
|------|:---:|:---:|------|
| `> [!NOTE]` / `[!TIP]` / `[!IMPORTANT]` / `[!WARNING]` / `[!CAUTION]` | ✅ | ✅ | 提示块（Gitee 实测渲染成 `markdown-alert-*` 带图标） |
| `<details><summary>…</summary>` | ✅ | ✅ | 折叠长清单 / 完整错误表 / 历史细节 |
| `<div align="center">…</div>` | ✅ | ✅ | 页首徽章居中、图表居中 |
| 表格 + 对齐标记 | ✅ | ✅ | 并列信息一律用表格 |
| 任务列表 `- [x]` | ✅ | ✅ | 检查清单 |
| `<img src width>` | ✅ | ✅ | 需要控制尺寸时用 HTML 替代 `![]()` |
| `[标签](相对路径)` | ✅ | ✅ | **站内链接唯一写法** |

> [!WARNING]
> **禁止的写法**（两站至少一边不支持，或已被判定为坏链）：
>
> - `[[Page|Label]]` —— GitHub Gollum 语法，Gitee 原样输出成纯文本
> - `> [!NOTE]` 之外的 HTML 表格 / 内联 `style=`（Gitee 会剥掉样式）
> - 裸 URL 直接成段（除邮箱与极少数例外，统一写 `<https://…>` 或做成链接文字）
> - 图片指向 `raw.githubusercontent.com`（国内常不可达），统一走 jsDelivr，见 `docs/agents-rules.md` §6.2

## 4. 结构：结论先行 + 编号章节

1. **每页开头先给结论**。不要「背景 → 原理 → 最后才说怎么办」。读者滑到第三节必须已经知道答案方向。
2. **`##` 章节一律编号**：`## 1. 环境要求`、`## 2. 安装`……编号让「第 3 节」这种交叉引用不会因为插节而错位。
3. 一节只讲一件事。**超过 40 行的小节必须拆**，或用 `<details>` 把细节折叠。
4. `###` 子节不编号，靠标题自解释。
5. 段首句即该段论点，不写「众所周知」「在当今」这类铺垫。

## 5. 五种提示块的选择口径

| 用哪个 | 什么时候 | 反例 |
|--------|----------|------|
| `> [!NOTE]` | 补充背景、口径说明、为什么这样设计 | 用它写「必须做 X」 |
| `> [!TIP]` | 更省事/更快的做法、可选优化 | 用它写会致命的前提 |
| `> [!IMPORTANT]` | 不照做就会用错、必须读到的前提 | 满页都是 IMPORTANT（等于没有） |
| `> [!WARNING]` | 会出错、会失效、已实测的坑 | 用它写数据丢失 |
| `> [!CAUTION]` | 会丢数据 / 破坏系统 / 不可逆 | 用它写一般性问题 |

> [!TIP]
> 每页的提示块**控制在 3 个以内**，且优先给「读了会少踩一个坑」的那条。提示块过多会让真正的警告失去分量。

## 6. 表格优先

并列的三项以上信息一律用表格，不用项目符号堆叠：

- 对象是「名称 → 作用」→ 两列表
- 对象是「选项 → 默认值 → 边界」→ 三列表
- 对象是「症状 → 先看这里」→ 两列表
- 状态用 ✅ / ❌ / ⚠️ / — 做视觉锚点，但**必须**在表内文字里再说一遍（emoji 不承载唯一语义，屏幕阅读器读不出来）

## 7. 折叠的用法

`<details>` 只用于「读者可能不看，但需要时必须在同一页」的内容：

- 完整错误文案对照表（超过 10 条）
- 逐文件的项目结构树
- 历史版本对照、完整环境变量清单
- 平台差异细节

**不要**折叠首次阅读就必须看到的内容（安装命令、必填前提、结论）。

```markdown
<details>
<summary><b>完整错误文案对照表（14 条）</b></summary>

| 报错原文 | 含义 | 处理 |
|----------|------|------|
| `...` | ... | ... |

</details>
```

## 8. 页脚导航（每页必须有）

```markdown
---

| ◀ 上一页 | 文档地图 | 下一页 ▶ |
|----------|----------|----------|
| [故障排查](troubleshooting.md) | [README 文档导航](../README.md#文档地图) | [架构设计](architecture.md) |
```

- README 与 Wiki 的 `_Sidebar` 充当「文档地图」，其余页面页脚必须给上下页。
- 结尾不留悬空小节；最后一个 `##` 章节之后直接接页脚分隔线。

## 9. 徽章与视觉元素

- 徽章只出现在 README 页首与 Wiki 的 Home，且**不超过 5 个**。
- 架构与数据流用 fenced code block（` ```text `）画 ASCII 图，不用图片——两站都能看，diff 也可读。
- 流程图保持**纵向单列**，宽度 ≤ 76 字符，避免窄屏横向滚动。
- 截图只放在 README「界面预览」与 Wiki Home，统一 `assets/screenshots/` 目录或 jsDelivr 地址。

## 10. 提交前的版面自检

- [ ] 页头三件套齐全（标题 / 一句话 / 对应源码或相关页面）
- [ ] `##` 章节均已编号，且编号连续
- [ ] 提示块 ≤ 3 个，类型选对
- [ ] 三项以上的并列信息已转成表格
- [ ] 站内链接全部是 `[标签](相对路径)`，无 `[[…]]`
- [ ] 页脚导航存在
- [ ] 去除头部与注释后正文 ≤ 300 行（R2）
- [ ] 全文无 `TODO` / `待补` / 占位符
- [ ] 两站渲染抽查：GitHub 网页 + `POST https://gitee.com/api/v5/markdown` 各看一次
